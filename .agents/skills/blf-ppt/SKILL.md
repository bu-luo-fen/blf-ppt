# BLF_PPT

以中文沟通为主。将不完整的想法、论文、项目材料或现有 PPT 转成有依据、可正式使用的汇报。用户可直接用自然语言启动，不要求填写表单或先写大纲。

## 规划

1. 先读现有材料与用户要求，辨认受众、场景、目标、核心问题、方法、结果、结论与局限。区分文献方法、计划工作和已完成成果；不编造结果、指标、引用或进展。证据不足的结论明确标注。
2. 提出故事线、章节和页数范围，记录术语、事实依据及可用的论文原图、数据图、实验截图。只有缺失信息会改变内容正确性或汇报方向时才问，优先一次问一个关键问题。内容方向有实质选择时请用户确认；已有明确方案则直接推进。
3. 有参考 PPT 时实际查看其页面比例、布局、配色、字体层级、留白、标志、页码、引用和不同页面类型；按用途借鉴，不机械逐页复制。为每页简记目的、主信息、表达形式、素材来源、待生图片、应保留的原生对象及重点检查项。优先确认整体故事线与视觉方向。
4. 多轮制作或跨窗口交接时，可在该 PPT 项目目录维护轻量 `project_brief.md`，只记已确认事实、方向、来源和待办；不要把项目私有材料写入本 Skill。

## 生图路线：必须在规划和逐页计划后、开始生图前决定

若用户尚未指定，提供两个不预设优先级的选项：**A** 在当前 Codex 任务中生图并继续组装；**B** 在独立 ChatGPT 对话窗口打磨图片，再将文件带回。解释操作差异，不承诺某条路线必然更省 Token 或更高质量。用户已指定时直接遵守，不重复询问。

- A：先确认当前任务真有可用生图工具，再显式调用。不能用文本描述或程序绘图冒充生图。
- B：交付可复制的图片任务说明，写清画幅、视觉目标、必要文字、结构关系、素材要求、禁止项、文件命名和返回清单；由用户完成跨窗口交接，收到后核对文件。不要假设聊天历史自动同步或能控制另一窗口。
- 所选路线不可用时说明限制与选项，取得用户新选择后再切换。不要默认引入 API Key、付费服务或 CLI 后备，也不要硬编码模型或额度。

批量生成图片前，先制作具有代表性的样张，检查视觉风格、图中文字清晰度、结构正确性及放入目标页面后的组合效果。视觉方向有重要选择时先请用户确认；用户已明确授权快速制作时可简化确认，但仍须完成质量检查。

方法框架、流程、系统、模块关系、逻辑与概念图，即使可用形状绘制，也优先考虑图像生成以保证结构表达和视觉质量。真实实验、仿真、数据与论文原图优先保真使用并记来源，绝不生造貌似真实的证据。逐张核对术语、拼写、模块完整性、箭头、清晰度及与原材料的一致性。关键错误先归因，再整图微调或重绘；最多两轮有针对性的自动重绘，仍有关键问题时停止并与用户商定调整。不要默认局部遮字修补。

## 组装与验收

按已确认的模板和逐页计划制作。统一尺寸、字体、色彩、标题及引文风格。页眉、页脚、标题、页码、引用与固定标志优先用原生 PowerPoint 对象；常改文字尽量可编辑。复杂视觉主体可保留为独立图片，图片转可编辑只是可选增强。保留清晰度、比例与人工修改空间。

检查分两遍：先看全部页面缩略图的风格、节奏、密度及异常；再放大检查方法图、系统图、数据页、密集页、复杂原图与异常页。能渲染就实际渲染；不能渲染则说明限制并做结构及可行的人工检查。可运行 [scripts/audit_pptx.py](scripts/audit_pptx.py) 辅助检查结构；它不能证明科学或视觉正确性。

硬性验收：PPTX 可打开、页数符合计划、没有已知严重科学错误、核心图术语与关系正确、没有严重截断遮挡或不可读内容、必需素材未遗漏、重要来源可追溯、无影响使用的占位符或结构问题。严重问题返工；普通装饰瑕疵可记录。默认交付 PPTX，仅在用户要求或确有价值时增加 PDF 等。报告文件位置、执行过的检查、修复、遗留问题和未能检查的项目，状态用 **通过 / 有条件通过 / 未通过**。不得把未执行的视觉检查写成通过。
